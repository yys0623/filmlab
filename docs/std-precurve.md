# STD v4: 단일 톤 선행 커브

> Historical study. Current STD delivery uses the model-specific V-Log Alchemy adapter; see [camera STD](camera-std.md). The measurements below describe the former implementation.

이 변경은 로컬 검토용이다. 기존 JpgToneProtection을 제거하고, 원래 색 렌더를 실행하기 **전에** 회색 응답의 역함수를 적용한다. 현재 내려받는 VLOG `.cube` 파일을 사면체 보간한 계산을 기준으로 삼는다. 연속 엔진을 정답으로 사용하는 방식은 아니며, VLOG 파일 자체와 그 안의 기존 필름·인화 처리, 색역 압축은 변경하지 않는다.

## 검토 의견

- 수용: 이미 렌더링된 STD/sRGB 사진의 감마만 풀어서 장면 반사값으로 취급하면 카메라 톤에 렌더 톤이 추가된다. 기존 `JpgToneProtection`의 중성색 빼기, 밝기 비율에 따른 채도 게인, OKLab 밝기 제한 및 최종 gamut mapping은 원본 렌더의 색을 추가로 바꾼다. 새 STD에서는 전부 제거한다.
- 수용하되 해석 제한: 회색 응답의 선행 역산은 톤을 한 번으로 정리하는 명시적 작업 가정이다. Panasonic Standard의 실제 카메라 처리나 필름 특성을 역측정한 것은 아니다. 동일 1D 함수를 각 RGB 채널에 적용해도 유채색의 색상과 채도가 보존된다고 보장할 수 없다.
- 수정: `R(P(T(x)))`를 만든 뒤 `R(P(x))`와 RGB가 같아야 한다는 조건은 T가 항등함수일 때만 맞다. A와 B 검증은 **같은 T를 포함한 독립 기준** `R(P(T(x)))`와 비교한다. T를 뺀 비교 결과도 별도로 기록하되 구현 오차로 판정하지 않는다.
- 수정: 중간톤 OKLab L 범위만으로 B의 하이라이트 커브가 비활성이라고 판단할 수 없다. 픽셀의 개별 RGB 채널은 18% 선형값보다 밝을 수 있기 때문이다.
- 수정: 종이 검정이 0보다 밝다면 B에서 ‘암부 전체 항등’, ‘원래 종이 검정 유지’, ‘암부 모든 단계 구분’을 동시에 만족시킬 수 없다. B는 P의 유효 범위 아래에서 원래 검정으로 포화한다. 끝단 디테일 보존 검사는 A에 적용한다.
- 수정: A가 선형광에서 상대 톤을 유지해도 8비트 출력에서 모든 인접 입력 단계가 다른 정수로 나오는 것은 불가능할 수 있다. 축소된 출력 범위에 256단계를 배치하기 때문이다. 부동소수점에서의 엄격한 증가, 8비트 반복값, 33³ 보간 오차를 나눠 보고한다.
- 판정 유보: 제시된 ‘채도 15–30%’, ‘변화량 1.1–2.7배’, 방향 반전 빈도는 측정 마스크·정의·기준에 의존한다. 저장된 이전 파일과 사용자 사진으로 다시 계산하며 그 범위를 보편적 사실로 인용하지 않는다.

## 정확한 계약

`D`는 sRGB 디코드, `E`는 sRGB 인코드다. 출력 RGB를 먼저 선형으로 변환한 후 Y를 계산한다. encoded RGB에 가중치를 곧바로 곱한 값은 이 정의의 Y가 아니다.

```text
F(x) = VLogEncode(D(x) @ sRGB_to_VGamut.T)
R(x) = tetrahedral(exported_VLOG_cube, F(x))
N(t) = E(0.2126 D(R(t,t,t).R) + 0.7152 D(R(t,t,t).G) + 0.0722 D(R(t,t,t).B))
P = inverse(monotone(N))
STD_A(x) = R(P(T_A(x)))
STD_B(x) = R(P(T_B(x)))
```

N은 encoded 회색 0..1에서 균일하게 4,097점 계산하고 누적 최댓값으로 단조성을 강제한다. 현재 238개 원본의 N은 모두 엄격히 증가해 실제 단조 보정량은 0이다. 평탄 구간이 있는 다른 입력에서는 상승 구간 사이의 일반화 역함수를 쓰며, 존재하지 않는 계조를 인위적인 작은 기울기로 만들지 않는다. 실제 흰색 끝점이 이전 피크보다 낮아 A의 끝점 계약과 충돌하면 생성을 거부한다.

P와 T는 **RGB 각 채널에 동일한 스칼라 함수**로 적용한다. 최종 R의 RGB는 수정 없이 반환한다. 중성색 제거, 채도 게인, 채도 클리핑 배율, OKLab 밝기 제한, tanh, TONE_RETENTION, 최종 흑백 늘이기, 이미지별 통계 및 자동 보정은 새 경로에 없다. `pipeline/jpg.py`는 이전 방식의 회귀 비교용으로만 보존한다.

공통 선행 커브는 기존 148개 모델과 FUJIFILM 기반 90개에 모두 적용한다. 후지 STD는 기존의 PROVIA 공통 중성 응답 역산을 새 P 앞에 중복 적용하지 않는다. 이미 생성된 FUJI VLOG 경로에는 V-Gamut/V-Log → F-Gamut/F-Log2 → 공식 LUT → 선택한 인화 모델 → sRGB가 들어 있다. 인화 모델의 기존 가정은 VLOG와 함께 그대로 남는다.

## A: 인화지 범위

```text
b = D(N(0)), w = D(N(1))
T_A(x) = E(b + (w-b) * D(x))
```

휘도의 검정·흰색을 0/255로 펴지 않는다. 원본 렌더가 회색에 주는 R/G/B 차이도 유지된다. 여기서 b/w는 입력 0..1과 F를 통해 **도달하는 렌더의 중성 끝점**이며, 종이의 물리적 Dmax/Dmin 측정값이라고 부르면 안 된다. 슬라이드·디지털·인화지 없는 후지에도 같은 렌더 범위 정의를 쓴다.

## B: 18% 회색 유지

m=0.18은 사진의 기준 회색이며 자유롭게 조정하는 강도 계수가 아니다. 정확한 sRGB 인코딩은 117.6458/255로, 8비트 118은 근삿값이다. 기준은 RGB 채널 모두가 118이어야 한다는 뜻이 아니라 **선형 Y가 0.18**이어야 한다는 뜻이다. 중성색 캐스트는 유지된다.

하이라이트 롤오프는 아래 유리함수다. 파라미터는 k 하나이고, 각 룩의 흰색 w로부터 자동으로 정한다.

```text
y = D(x)
k = (1-w)/(w-m)
T_B_linear(y) = y                                  (y <= m)
              = m+(y-m)/(1+k*(y-m)/(1-m))            (y > m)
T_B(x) = E(T_B_linear(D(x)))
```

근거: T(m)=m, T′(m)=1, T(1)=w를 동시에 만족한다. 연결점은 C1 연속이고 w>m이면 도함수는 양수다. w<=m이면 B를 만들지 않는다. 현재 238개에는 이 예외가 없다. **각 룩의 실제 k와 b/w 값은 A/B provenance 및 검증 표에 기록한다.** 예를 들어 Portra 400 + Portra Endura의 k는 약 0.791151이다.

B의 입력 목표값이 N(0)보다 낮으면 P는 0으로 포화한다. 따라서 검정 위에 바닥이 있는 필름·인화 모델의 가장 어두운 영역은 뭉칠 수 있다. 2026-11-03 처음에는 B를 기본으로 선택했으나, 같은 날 필름 간 컬러 차이를 우선하는 사용자 선택에 따라 기본값을 Legacy v3로 복원했다. A/B 수식과 파일은 변경하지 않았으며 둘 다 비교용 선택지로 유지한다. A는 출력 범위 전체의 상대 계조 유지가 목적이면 선택할 수 있다. B를 밝기 보존과 끝단 보존을 동시에 달성한 버전으로 설명하지 않는다.

## 파일과 재현

- `####VLOG.cube`: 기존 바이트 유지.
- `####STD.cube`: A, 인화지/렌더 범위.
- `####STB.cube`: B, 중간회색 유지. LUMIX의 8자 파일명 길이에 맞춘 별도 파일.
- `####LUTS.zip`: 세 LUT와 QA·provenance·권리 안내.
- `qa.singleTonePrecurve`, `qa.stdVariants.A/B`: 수식·범위·k·가정.
- `source.sha256`: 선행 커브를 산출한 **디스크 VLOG 파일**의 SHA-256.
- `artifacts/std-precurve-baseline/`: 작업 직전 STD v3·메타데이터·이미지·ZIP을 최초 한 번 백업. 재실행은 이를 덮어쓰지 않는다.

```bash
.venv/bin/python -m pipeline.generate_precurve
.venv/bin/python -m pipeline.audit_precurve
npm test
npm run build
```

`stdVsDirectEngine`라는 예전 JSON 키는 UI 호환 때문에 남아 있지만, v4에서 그 기준은 **파일 기반 VLOG + 분석적 F/P/T의 합성**이다. 연속 spektrafilm 엔진 또는 실물 정확도라는 뜻이 아니다. 최종 33³ STD 보간 오차와 원본 33³ VLOG의 오차가 존재한다. 미리보기는 다운로드용 STD 파일을 직접 읽고 사면체 보간하며, 서버나 CSS에서 추가 톤을 적용하지 않는다.

## 실측 한계

Panasonic STD의 전체 톤 곡선을 확보하지 못했으므로 **카메라 톤이 필름 톤 자리를 대신한다는 가정의 근사**다. 실제 검증은 같은 장면을 통제된 조명·노출·화이트밸런스로 **V-Log + VLOG LUT**와 **STD + 새 STD LUT**로 촬영해 비교해야 한다. 이 실기 검증은 **미검증**이다. 이미 잘린 고광·암부·색역은 되살릴 수 없다.

수치와 비교 사진은 [검증 보고서](std-precurve-validation.md)에서 확인한다.
